  Send visitors from old or moved addresses to new ones, one page at a time or a

Redirects send visitors from one address on your documentation site to another. Use them when you rename or move pages, so old links, bookmarks and search results keep working. A dynamic redirect moves many addresses with one rule, such as a whole section after a migration or a version change.

## When to use redirects

Common use cases for redirects include:

- **Page moves**: Redirect old URLs when you reorganize your documentation structure

- **URL changes**: Maintain links when renaming pages or changing URL slugs

- **Legacy support**: Keep old bookmarks and external links working

- **Content consolidation**: Redirect multiple old pages to a single new page

- **Version migrations**: Redirect users from deprecated API versions to current ones

- **Platform migrations**: Send every address of your old documentation site to its new place with a few [dynamic redirects](#dynamic-redirects)

## Add a redirect from the Editor

<Steps>
  <Step title="Open the Redirects settings" icon="settings">

  In the Editor, click **Site Config** in the top toolbar, then select **Redirects** from the left sidebar.

  </Step>
  <Step title="Add a rule" icon="plus">

  Under **Redirect Rules**, click **Add Redirect**. Enter the old address as the **Source** and the new one as the **Destination**. Both start with `/`.

  To move a whole section, use a [wildcard](#wildcards): `/beta/:slug*` as the source and `/v2/:slug*` as the destination.

  </Step>
  <Step title="Choose a status code" icon="list">

  Keep **Status code** at `308` for a permanent move, or pick another [status code](#status-codes). Then click **Add Redirect**.

  </Step>
  <Step title="Publish" icon="rocket">

  Click **Publish**. The redirect works on your live site once it deploys.

  </Step>
</Steps>

Hover the info icon next to **Source** for a reminder of the pattern syntax. The form refuses a rule written in a way the site can't use: a source with two `*`, a `?` or `#` in a source, or a destination that uses a parameter its source doesn't have. It doesn't check where a rule sends visitors, so watch for [redirect loops](#avoid-redirect-loops) and [patterns that match existing pages](#patterns-and-existing-pages).

## Add redirects in documentation.json

Redirects are configured in your `documentation.json` file under the `redirects` property:

```json
{
  "redirects": [
    {
      "source": "/old-page",
      "destination": "/new-page"
    }
  ]
}
```

## Redirect properties

| Property      | Type                       | Required | Description                                                                                                                                       |
| ------------- | -------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source`      | `string`                   | Yes      | The address to match, starting with `/`. Can use a [parameter, a wildcard or a partial wildcard](#dynamic-redirects) to match many addresses.     |
| `destination` | `string`                   | Yes      | Where visitors go: a path on your site or a full URL. Can reuse what the source's parameters and wildcards matched, and can end in a query or anchor. |
| `statusCode`  | `301 \| 302 \| 307 \| 308` | No       | HTTP status code for the redirect. Defaults to `308`.                                                                                             |

## Status codes

Choose the appropriate status code based on your redirect scenario:

| Code  | Name               | Use Case                                                                                               |
| ----- | ------------------ | ------------------------------------------------------------------------------------------------------ |
| `301` | Moved Permanently  | Permanent redirect. May change request method to GET. Best for SEO when content has permanently moved. |
| `302` | Found              | Temporary redirect. May change request method to GET. Use for temporary moves.                         |
| `307` | Temporary Redirect | Temporary redirect that preserves the request method. Use for temporary moves with POST/PUT requests.  |
| `308` | Permanent Redirect | Permanent redirect that preserves the request method. **Default**. Best for permanent moves.           |

<Callout kind="tip" collapsed="false">
  Use `308` (the default) for most permanent redirects. It's the modern
  replacement for `301` and preserves the HTTP method, which is important for
  API documentation.
</Callout>

## Basic redirects

### Simple page redirect

Redirect a single page to a new location:

```json
{
  "redirects": [
    {
      "source": "/old-page",
      "destination": "/new-page"
    }
  ]
}
```

### Multiple redirects

Define multiple redirects in the array:

```json
{
  "redirects": [
    {
      "source": "/getting-started",
      "destination": "/docs/quickstart"
    },
    {
      "source": "/api-docs",
      "destination": "/api-reference"
    },
    {
      "source": "/faq",
      "destination": "/support/faqs"
    }
  ]
}
```

### Redirect with custom status code

Specify a status code for temporary or specific redirect behaviors:

```json
{
  "redirects": [
    {
      "source": "/maintenance",
      "destination": "/status",
      "statusCode": 307
    },
    {
      "source": "/legacy-api",
      "destination": "/v2/api",
      "statusCode": 301
    }
  ]
}
```

## Dynamic redirects

A dynamic redirect matches many addresses with one rule. Its source uses a parameter, a wildcard or a partial wildcard, and its destination can reuse what they matched.

| Pattern          | Written as        | Matches                                         | Example source         |
| ---------------- | ----------------- | ----------------------------------------------- | ---------------------- |
| Parameter        | `:name`           | Exactly one segment                             | `/docs/:slug`          |
| Wildcard         | `:name*`          | Any number of segments, including none          | `/beta/:slug*`         |
| Partial wildcard | `*` in a segment  | Any text in that one segment                    | `/articles/concepts-*` |

A segment is the part of an address between two slashes: `/docs/api/users` has three.

### Parameters

A parameter, written `:name`, matches exactly one segment. Use the same name in the destination to carry its value over:

```json
{
  "redirects": [
    {
      "source": "/docs/:slug",
      "destination": "/documentation/:slug"
    }
  ]
}
```

This redirect matches:

- `/docs/quickstart` → `/documentation/quickstart`

- `/docs/api-reference` → `/documentation/api-reference`

It doesn't match `/docs/api/users`, which has two segments after `/docs/`. Use a [wildcard](#wildcards) for that.

A source can have several parameters, and the destination can use them in any order or leave some out:

```json
{
  "redirects": [
    {
      "source": "/api/:version/:endpoint",
      "destination": "/reference/:version/:endpoint"
    },
    {
      "source": "/blog/:year/:month/:slug",
      "destination": "/articles/:slug"
    }
  ]
}
```

- `/api/v1/users` → `/reference/v1/users`

- `/blog/2024/01/my-post` → `/articles/my-post`

### Wildcards

A wildcard, written `:name*`, matches any number of segments, including none. Use it to move a whole section with one rule:

```json
{
  "redirects": [
    {
      "source": "/beta/:slug*",
      "destination": "/v2/:slug*"
    }
  ]
}
```

This redirect matches:

- `/beta/introduction` → `/v2/introduction`

- `/beta/api/users/create` → `/v2/api/users/create`

- `/beta` → `/v2`

The wildcard can also sit between fixed segments. `/docs/:path*/edit` matches `/docs/guides/setup/edit` and passes `guides/setup` on as `:path*`.

To send every address of an old site to a new one, start the source with the wildcard:

```json
{
  "redirects": [
    {
      "source": "/:slug*",
      "destination": "https://docs.example.com/:slug*"
    }
  ]
}
```

### Partial wildcards

A partial wildcard, written `*` inside a segment, matches any text where the `*` is, within that one segment. Use it for a family of pages whose names share a beginning:

```json
{
  "redirects": [
    {
      "source": "/articles/concepts-*",
      "destination": "/collections/overview"
    }
  ]
}
```

This sends `/articles/concepts-getting-started` and `/articles/concepts-overview` to `/collections/overview`.

Put `*` in the destination to carry the matched text over:

```json
{
  "redirects": [
    {
      "source": "/old/article-*",
      "destination": "/new/article-*"
    }
  ]
}
```

This redirects `/old/article-123` to `/new/article-123`. It doesn't match `/old/article-123/details`, because a partial wildcard stays within one segment.

### Rules for dynamic redirects

- A source has at most one `*`, so one wildcard or one partial wildcard. A source with more is skipped. Parameters don't count toward this.

- A source can't include a query (`?tab=api`) or an anchor (`#setup`). A destination can end in either.

- Every parameter, wildcard and `*` in the destination must be in the source. The Editor refuses a destination that uses one the source doesn't have.

## Pattern matching behavior

Understanding how redirects match URLs helps you configure them correctly.

### Trailing slashes

Trailing slashes are normalized during matching. Both `/docs/` and `/docs` will match a source pattern of `/docs`:

```json
{
  "redirects": [
    {
      "source": "/docs",
      "destination": "/documentation"
    }
  ]
}
```

Matches both:

- `/docs` → `/documentation`

- `/docs/` → `/documentation`

### Case sensitivity

Path matching is **case-sensitive**. `/Docs` will not match a source of `/docs`:

```json
{
  "redirects": [
    {
      "source": "/docs",
      "destination": "/documentation"
    }
  ]
}
```

- `/docs` → `/documentation` ✓

- `/Docs` → No match ✗

### Segment count

Without a wildcard, a source and an address must have the same number of segments. A [wildcard](#wildcards) matches any number:

- `/docs/:slug` matches `/docs/quickstart`, but not `/docs/api/users`

- `/docs/:slug*` matches both

## Processing order

When several redirects match one address, the site picks one in this order:

1. Redirects with an exact source, without a parameter or `*`

2. Redirects with a partial wildcard

3. Redirects with a parameter or a wildcard

Within each group, the first matching redirect in the list wins, so put a narrower pattern before a broader one.

```json
{
  "redirects": [
    {
      "source": "/docs/:slug*",
      "destination": "/documentation/:slug*"
    },
    {
      "source": "/docs/api/deprecated",
      "destination": "/docs/api/v2"
    }
  ]
}
```

In this example:

- `/docs/api/deprecated` goes to `/docs/api/v2`, because an exact source is tried first, even though it's listed second

- `/docs/quickstart` matches the wildcard and goes to `/documentation/quickstart`

## Avoid redirect loops

A destination that its own source matches again sends visitors around forever. `/docs/:slug*` to `/docs/v2/:slug*` turns `/docs/intro` into `/docs/v2/intro`, which the same rule turns into `/docs/v2/v2/intro`, and so on. Point the destination outside the source, for example `/v2/:slug*`.

Two redirects that send visitors back and forth loop too, such as `/docs/:slug*` to `/help/:slug*` together with `/help/:slug*` to `/docs/:slug*`.

The Editor doesn't check for loops. The **Broken Link Audit** [automation](/ai/automations) reports links on your pages that lead into a redirect chain that never ends.

### Patterns and existing pages

A pattern matches every address it describes, including pages that still exist. `/api/:slug*` sends visitors away from `/api/overview` even while that page is in your navigation. Keep a dynamic redirect's source to addresses that no longer have pages.

## Subpath deployments

If your documentation is deployed at a subpath (e.g., `example.com/docs`), redirects are automatically adjusted:

- The subpath is prepended to the `source` for matching

- The subpath is prepended to the `destination` if not already present

You don't need to include the subpath in your redirect configuration:

```json
{
  "redirects": [
    {
      "source": "/old-page",
      "destination": "/new-page"
    }
  ]
}
```

For a subpath deployment at `/docs`:

- Request to `/docs/old-page` → Redirects to `/docs/new-page`

Dynamic redirects work the same way: `/beta/:slug*` to `/v2/:slug*` redirects `/docs/beta/intro` to `/docs/v2/intro`.

## Examples

### Documentation restructure

When a section moves, one wildcard covers every page in it. Add an exact redirect for any page that also got a new name, because exact sources are tried first:

```json
{
  "redirects": [
    {
      "source": "/integrations-and-workflows/:slug*",
      "destination": "/integrations/:slug*"
    },
    {
      "source": "/integrations-and-workflows/github-integration",
      "destination": "/integrations/github"
    }
  ]
}
```

### API version migration

When deprecating an API version:

```json
{
  "redirects": [
    {
      "source": "/api/v1/:slug*",
      "destination": "/api/v2/:slug*",
      "statusCode": 301
    }
  ]
}
```

This covers `/api/v1` itself and every page below it.

### Migration from another platform

When your old site kept its pages under a prefix, such as `/en/latest/`, send them to the same pages on your new site:

```json
{
  "redirects": [
    {
      "source": "/en/latest/:slug*",
      "destination": "/:slug*"
    }
  ]
}
```

### Content consolidation

When merging multiple pages into one:

```json
{
  "redirects": [
    {
      "source": "/troubleshooting/*",
      "destination": "/support/troubleshooting"
    },
    {
      "source": "/help/common-issues",
      "destination": "/support/troubleshooting"
    }
  ]
}
```

### Temporary maintenance redirect

When temporarily redirecting during maintenance:

```json
{
  "redirects": [
    {
      "source": "/api-playground",
      "destination": "/maintenance",
      "statusCode": 307
    }
  ]
}
```

## Best practices

<ExpandableGroup>
  <Expandable title="Keep redirects organized" default-open="false">
    Group related redirects together and add comments in your configuration management system to explain why each redirect exists:

    - Group by feature or section

    - Document the date and reason for each redirect

    - Review and clean up outdated redirects periodically
  </Expandable>

  <Expandable title="Use one wildcard instead of many redirects" default-open="false">
    When a whole section moves, one [wildcard](#wildcards) replaces a redirect per page and also covers pages you didn't list, such as old deep links. Keep exact redirects only for pages that also got a new name.
  </Expandable>

  <Expandable title="Use permanent redirects for SEO" default-open="false">
    When content has permanently moved, use status code `301` or `308` to transfer SEO value to the new URL. Search engines will update their indexes to point to the new location.
  </Expandable>

  <Expandable title="Test redirects before deploying" default-open="false">
    Verify your redirect patterns work as expected:

    1. Check that source patterns match intended URLs

    2. Verify destination URLs exist and are correct

    3. Test with and without trailing slashes

    4. For a wildcard, test an address one segment deep, one several segments deep, and the section's own address
  </Expandable>

  <Expandable title="Avoid redirect chains" default-open="false">
    Don't create redirects that point to other redirects. Each hop adds latency and can confuse search engines:

    **Avoid:**

    - `/page-a` → `/page-b` → `/page-c`

    **Better:**

    - `/page-a` → `/page-c`

    - `/page-b` → `/page-c`
  </Expandable>

  <Expandable title="Monitor redirect performance" default-open="false">
    Keep track of how often redirects are triggered. High-traffic redirects might indicate:

    - External links that should be updated

    - Internal links that need fixing

    - Popular old URLs that users still bookmark
  </Expandable>
</ExpandableGroup>

## Troubleshooting

<ExpandableGroup>
  <Expandable title="Redirect not working" default-open="false">
    If your redirect isn't triggering:

    - Verify the source path matches exactly (case-sensitive)

    - A parameter matches one segment only. Use a [wildcard](#wildcards) for deeper addresses

    - Check that the source has at most one `*`

    - Check whether a redirect earlier in the [processing order](#processing-order) matches first

    - Clear your browser cache and test in an incognito window

    - Re-publish your documentation after configuration changes
  </Expandable>

  <Expandable title="A page now redirects away" default-open="false">
    A dynamic redirect matches pages that still exist. Narrow its source so it covers only the old addresses. See [Patterns and existing pages](#patterns-and-existing-pages).
  </Expandable>

  <Expandable title="Wrong destination URL" default-open="false">
    If redirects go to unexpected locations:

    - Check for typos in the destination path

    - Verify parameter and wildcard names match between source and destination

    - Ensure subpath configuration is correct for your deployment type
  </Expandable>

  <Expandable title="Redirect loops" default-open="false">
    If you're experiencing infinite redirect loops:

    - Check that the destination isn't inside its own source, such as `/docs/:slug*` to `/docs/v2/:slug*`

    - Check that the destination doesn't match another redirect's source

    - Review all redirects that involve the affected URLs

    See [Avoid redirect loops](#avoid-redirect-loops).
  </Expandable>

  <Expandable title="Dynamic parameters not working" default-open="false">
    If parameter substitution fails:

    - Ensure parameter names start with `:` in the source (e.g., `:slug`), and wildcards end with `*` (e.g., `:slug*`)

    - Use the exact same name in the destination

    - Verify the source pattern has the correct number of segments, or use a wildcard
  </Expandable>
</ExpandableGroup>
