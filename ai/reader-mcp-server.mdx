## Serve your documentation to AI agents

The Reader MCP Server is your own MCP endpoint, served from your documentation domain. It gives MCP-compatible agents read-only access to your published documentation so they can search it, read full pages, and follow your site's navigation, without any ability to change it. Public documentation is available without authentication. Private, partial, and password-protected documentation is accessible through two authentication types: OAuth 2.1 for interactive client connections, and machine-to-machine credentials for automated access without a browser.

This is the server your **readers** connect to: customers, support teams, solution engineers, and internal users, along with the AI agents they work in. If you are looking for the server your documentation team connects to in order to _write_ docs, see the [Authoring MCP Server](/ai/authoring-mcp-server).

<Callout kind="note" collapsed="false">
  The Reader MCP Server was previously called the **Docs MCP Server**. Only the name changed. Your endpoint, its behavior, and any existing client configurations continue to work unchanged.
</Callout>

<Callout kind="info" collapsed="false">
  The Reader MCP Server is read-only. It does not create, update, delete, or reorganize content, and it does not expose branch management, deployments, or dashboard actions. For those workflows, use the [Authoring MCP Server](/ai/authoring-mcp-server).
</Callout>

## Find your endpoint

The Reader MCP Server becomes available as soon as you publish your documentation. There is nothing to provision or enable.

You can find your endpoint in the dashboard under **MCP Servers** in the sidebar. It follows the same shape as your documentation URL:

- `https://docs.yourdomain.com/_mcp`
- `https://yourdomain.com/docs/_mcp`

If your documentation has [access control](/customize/access-control/overview) enabled, your authenticated endpoint is:

- `https://docs.yourdomain.com/_mcp/auth`
- `https://yourdomain.com/docs/_mcp/auth`

Partially private sites expose both endpoints: `/_mcp` for public content and `/_mcp/auth` for gated content.

## Understand what it can access

The Reader MCP Server serves your published documentation. It sits in front of your published site, not your authoring environment.

For **public** documentation, the server exposes content that is open to anyone. No authentication is required.

For **private, partial, or password-protected** documentation, the `/_mcp/auth` endpoint supports two authentication types:

- **OAuth 2.1**: For interactive connections where a user is present. The client opens a browser, the user approves the connection and signs in through your site's existing authentication method (password, Documentation.AI, JWT, or OAuth 2.0), and a credential is minted automatically.
- **Machine-to-machine credentials**: For automated access without a browser. An admin creates a credential in the dashboard that produces a token with a `dmcp_` prefix. The token authenticates directly with the `/_mcp/auth` endpoint, scoped by the access roles assigned at creation time.

Both types produce a token the client uses for subsequent requests. Access is scoped by the roles assigned to the credential or OAuth session.

Because the server is read-only, it works well when you want grounded answers from trusted documentation while keeping editing controls entirely separate.

<Callout kind="tip" collapsed="false">
  The Reader MCP Server is not connected to Documentation.AI workspace roles. The **Viewer** role on the [Authoring MCP Server](/ai/authoring-mcp-server) is unrelated: that role governs your team's access to the project, while the Reader MCP Server serves what your site publishes.
</Callout>

## Authentication for private documentation

When your documentation has [access control](/customize/access-control/overview) enabled, the `/_mcp/auth` endpoint supports two authentication types: OAuth 2.1 for interactive client connections, and machine-to-machine credentials for automated access without a browser.

### OAuth 2.1

OAuth 2.1 works with any authentication method you have configured (password, Documentation.AI, JWT, or OAuth 2.0). The flow is handled automatically by supported MCP clients.

<Steps>
  <Step title="Connect your MCP client to the authenticated endpoint" icon="link" title-type="p">
    Use the `/_mcp/auth` endpoint instead of `/_mcp`. For partially private sites, use `/_mcp/auth` to access both public and gated content.
  </Step>

  <Step title="Approve the connection in your browser" icon="check-circle" title-type="p">
    The MCP client opens a browser window showing a consent screen. Review the client name and the redirect URI, then approve the connection.
  </Step>

  <Step title="Sign in through your site's authentication" icon="lock" title-type="p">
    After approving, you are redirected to your documentation site's sign-in page. Complete authentication using whatever method your site uses (password, Documentation.AI, JWT, or OAuth 2.0).
  </Step>

  <Step title="Start using the server" icon="play" title-type="p">
    Once authenticated, the client receives a token and can search and retrieve content from your documentation. The token is valid until it expires or is revoked.
  </Step>
</Steps>

Built-in support for Claude Desktop, Cursor, VS Code, Claude Web, and ChatGPT connectors means these clients handle the OAuth flow automatically. No manual token management is needed for those clients.

<Callout kind="info" collapsed="false">
  For password-gated sites, a dedicated sign-in page is shown within the OAuth flow so users can enter their credentials without leaving the MCP authentication process.
</Callout>

<Callout kind="info" collapsed="false">
  On sites that use [Documentation.AI authentication](/customize/access-control/documentation-ai), a connection stays tied to the person who signed in. If they're removed from your organization, the client loses access within 5 minutes. Machine-to-machine credentials aren't tied to a person and keep working until they expire or you revoke them.
</Callout>

#### Callback URLs

For MCP clients that use OAuth redirect URIs, manage the allowed callback URLs from the dashboard. Built-in URIs for Claude, ChatGPT, and Cursor are included by default. Add custom URIs for other clients as needed. Up to 50 callback URLs are supported.

### Machine-to-machine credentials

For clients that do not support OAuth 2.1 directly, or for automated access where no browser is available, admins can create and manage machine-to-machine credentials from the dashboard. Each credential produces a token with a `dmcp_` prefix that authenticates directly with the `/_mcp/auth` endpoint.

<Callout kind="info" collapsed="false">
  Up to 25 active machine-to-machine credentials are supported per documentation project.
</Callout>

#### Create a credential

1. Go to **MCP Servers** in the dashboard sidebar.
2. Under the Reader MCP panel, click **Create Credential**.
3. Enter a name, select access roles, and choose an expiry: 30 days, 60 days, 90 days, 180 days, 1 year, or never.
4. Click **Create** to generate the credential.

The token is shown **once** after creation. Copy it immediately and store it securely. A ready-made client configuration JSON is also provided so you can paste it directly into your MCP client.

<Callout kind="alert" collapsed="false">
  The token cannot be retrieved later. If you lose it, revoke the credential and create a new one.
</Callout>

<Callout kind="info" collapsed="false">
  Roles are matched case-insensitively against the roles declared in your site configuration. The declared spelling is stored, so `Engineering`, `engineering`, and `ENGINEERING` all match the same role.
</Callout>

#### View and edit credentials

All credentials appear in a table showing the name, source, access roles, last used time, and expiry. You can edit access roles on an existing credential without re-issuing the token.

#### Revoke a credential

Revoke individual credentials from the credential table, or revoke all credentials at once. Revocation takes effect immediately.

<Callout kind="alert" collapsed="false">
  Revoking a credential is permanent. Any client using that token will lose access immediately. Create a new credential to restore access.
</Callout>

## Configure your MCP client

Add your endpoint to any MCP-compatible client. Replace `docs.yourdomain.com` with your own documentation domain.

<CodeGroup show-lines="true">
  ```json
  {
    "mcpServers": {
      "my-docs": {
        "command": "npx",
        "args": [
          "mcp-remote",
          "https://docs.yourdomain.com/_mcp",
          "--timeout",
          "120000"
        ]
      }
    }
  }
  ```

  ```bash
  claude mcp add my-docs \
    --transport http \
    --url https://docs.yourdomain.com/_mcp
  ```

  ```json
  {
    "mcpServers": {
      "my-docs": {
        "command": "npx",
        "args": [
          "mcp-remote",
          "https://docs.yourdomain.com/_mcp",
          "--timeout",
          "120000"
        ]
      }
    }
  }
  ```
</CodeGroup>

For Claude Desktop, add the configuration to `claude_desktop_config.json`. For Cursor, add it to your `mcp.json`. For Claude Code, run the command from your terminal, or add the same JSON to a `.mcp.json` file in your project root.

<Callout kind="info" collapsed="false">
  If your documentation has access control enabled, replace `/_mcp` with `/_mcp/auth` in the endpoint URL. Clients with built-in OAuth support (Claude Desktop, Cursor, VS Code, ChatGPT) will handle the authentication flow automatically. For clients without OAuth support, create a machine-to-machine credential and use the provided token in your client configuration.
</Callout>

<Callout kind="tip" collapsed="false">
  You can copy your endpoint straight from a documentation page using the **Copy MCP server URL** page action. See [Page Actions](/ai/page-actions).
</Callout>

## Tools reference

The server provides read-only tools. Your MCP client discovers them and their parameters when it connects, so you don't need to configure anything beyond the endpoint.

| Tool | What it does |
| --- | --- |
| `search_documentation` | Finds the sections that answer a question |
| `read_pages` | Returns full pages, several in one call |
| `get_navigation` | Shows how pages are grouped in your site's navigation |
| `list_pages` | Lists the pages the connection can read, by folder. Offered only when your site's navigation can't be loaded, in place of `get_navigation` |

Agents usually search first, then read the full pages behind the results, then open a result's navigation group to find related pages. For example, asked how to rotate an API key, an agent searches for "rotate API key", reads `/guides/api-keys.mdx`, and opens that page's group to check the pages beside it.

Every tool returns only what the connection can read: public content on `/_mcp`, and content allowed by the connection's access roles on `/_mcp/auth`. A page the connection can't read is reported as not found, the same as a page that doesn't exist.

All tools read your last deployment. Changes that are still on a branch, or not yet deployed, don't appear.

### Search

<Expandable title="search_documentation" default-open="false">
  Searches your documentation by meaning and by keyword, and returns the matching sections rather than whole pages. Results also include the [external sources](/ai/external-sources) you've added to the AI Assistant.

  <ParamField body="query" param-type="string" required="true" deprecated="false" show-location="false">
    What to search for
  </ParamField>

  <ParamField body="limit" param-type="number" required="false" deprecated="false" show-location="false">
    Maximum number of results, from 1 to 20. Defaults to 10.
  </ParamField>

  <ParamField body="semanticRatio" param-type="number" required="false" deprecated="false" show-location="false">
    Balance between matching by meaning and matching exact keywords, from 0 to 1. Defaults to 0.75. Lower values favor exact matches.
  </ParamField>

  <ParamField body="version" param-type="string" required="false" deprecated="false" show-location="false">
    Search one version only. See [Versions, languages, and products](#versions-languages-and-products).
  </ParamField>

  <ParamField body="language" param-type="string" required="false" deprecated="false" show-location="false">
    Search one language only.
  </ParamField>

  <ParamField body="product" param-type="string" required="false" deprecated="false" show-location="false">
    Search one product only.
  </ParamField>

  The `version`, `language`, and `product` filters appear only on sites with more than one of each.

  Each result includes the section's text, its page title, and links to the section and its page for citing. Results from your documentation pages also include:

  - `path`: the page's path, to pass to `read_pages`
  - `navigation_pointer`: the page's place in your navigation, to pass to `get_navigation`
  - `version`, `language`, and `product`: where the page sits in your navigation
</Expandable>

### Browse and read

<Expandable title="read_pages" default-open="false">
  Returns full pages as Markdown, up to 20 in one call. Pass the paths that the other tools return, for example `/guides/intro.mdx`. A path without `.mdx`, a page's URL path such as `/api/auth`, or its full URL also works.

  <ParamField body="paths" param-type="array" required="true" deprecated="false" show-location="false">
    Page paths, up to 20
  </ParamField>

  <ParamField body="startLine" param-type="number" required="false" deprecated="false" show-location="false">
    Line to start each page from. Defaults to 1. Use it to continue a page that was cut off.
  </ParamField>

  Each reply is limited to 30 KB. A longer page is cut at the end of a line, and the reply gives the `startLine` that continues it. Pages that didn't fit are named in the reply so the agent can read them in the next call.
</Expandable>

<Expandable title="list_pages" default-open="false">
  Lists the pages the connection can read, with each page's path and title, sorted by path.

  A call returns up to 200 pages. When there are more, the first reply starts with each folder and its page count, and every reply gives the `offset` for the next pages.

  <ParamField body="folder" param-type="string" required="false" deprecated="false" show-location="false">
    Only pages under this folder, for example `/guides`. Omit it for the whole site.
  </ParamField>

  <ParamField body="offset" param-type="number" required="false" deprecated="false" show-location="false">
    Pages to skip, as given in the previous reply. Defaults to 0.
  </ParamField>

  <ParamField body="version" param-type="string" required="false" deprecated="false" show-location="false">
    List one version only. The `language` and `product` filters work the same way. See [Versions, languages, and products](#versions-languages-and-products).
  </ParamField>
</Expandable>

### Navigation

<Expandable title="get_navigation" default-open="false">
  Shows your site's navigation: products, versions, languages, tabs, groups, and pages. Each entry has a pointer such as `/navigation/tabs/0/groups/2/pages/1`. Removing the last two segments of a pointer gives its parent, so `/navigation/tabs/0/groups/2` is the group that page sits in.

  <ParamField body="pointer" param-type="string" required="false" deprecated="false" show-location="false">
    Entry to open. For a tab or group, returns everything beneath it. For a page, returns its group and the pages beside it. Omit it for an outline of the whole navigation.
  </ParamField>

  <ParamField body="depth" param-type="number" required="false" deprecated="false" show-location="false">
    Navigation levels to show below the entry. The outline shows 2 levels by default.
  </ParamField>

  <ParamField body="find" param-type="string" required="false" deprecated="false" show-location="false">
    Text to look for in entry titles and paths, ignoring case. Returns up to 50 matching entries, each with its pointer.
  </ParamField>

  The navigation shows only the pages the connection can read. On a site with access control, pointers count only those pages, so they can differ from the positions in your `documentation.json`.
</Expandable>

### Versions, languages, and products

If your site uses [dimensions](/organize/dimensions), `search_documentation` and `list_pages` accept `version`, `language`, and `product`. Each filter appears only when your site has more than one value for it, and it takes the names from your navigation, such as `v2` or `Spanish`. Names match regardless of case.

When an agent searches one version and nothing in it matches closely, the server searches your whole site and tells the agent the results come from elsewhere, so the answer can say so. The AI Assistant behaves the same way.

If you want searches to stay inside the requested version, language, or product, turn on [strict dimensions](/ai/ai-assistant#strict-dimensions). The server then keeps the search inside it and tells the agent when nothing there matched closely.

### Limits

| Limit | Value |
| --- | --- |
| Reply size | 30 KB per call |
| Pages per `list_pages` call | 200 |
| Pages per `read_pages` call | 20 |
| Matches per `get_navigation` search | 50 |
| Search results | 10 by default, at most 20 |

When a `read_pages` call asks for several very long pages, it can return fewer than 20. The reply names the pages to read next.

## Best-fit use cases

Choose the Reader MCP Server when the goal is documentation retrieval, not documentation management.

- **Customer-facing documentation**: Let customers connect AI agents to your published docs for product questions, onboarding, and API lookup.
- **Support and success workflows**: Help your team answer from the same published docs your customers use.
- **AI agents and copilots**: Add a retrieval layer over your docs so responses stay tied to current published content.

## Troubleshooting

<Expandable title="The endpoint returns a 404" default-open="false">
  The Reader MCP Server exists only for published documentation. If you have not deployed yet, publish first, then retry the connection. Also confirm you are using the `_mcp` path on the same domain your documentation is served from.
</Expandable>

<Expandable title="The client connects but returns no results" default-open="false">
  Search covers published content. If you recently added or edited pages, confirm the changes have been deployed rather than left on a branch. If your documentation is private, password-protected, or partially gated, make sure you are connecting to the `/_mcp/auth` endpoint. Complete the OAuth flow from a supported client, or use a machine-to-machine credential if your client does not support OAuth.
</Expandable>

<Expandable title="The client cannot discover the server" default-open="false">
  Some MCP clients require a remote-server bridge rather than a direct URL. If your client has no option to add a remote or HTTP server, use the `npx mcp-remote` configuration shown above.
</Expandable>

<Expandable title="read_pages says a page is not found" default-open="false">
  The reply reads `Not found: <path>`. The path is wrong, or the connection can't read that page. Use a path that `search_documentation` or `get_navigation` returned. If the page is gated, connect to `/_mcp/auth` with a credential whose access roles include the page.
</Expandable>

<Expandable title="A search or page list says the version is unknown" default-open="false">
  The reply reads `Unknown version` and lists the versions your site has. Use one of those names. Languages and products work the same way.
</Expandable>

<Expandable title="get_navigation says there is no entry at a pointer" default-open="false">
  The reply reads `No navigation entry at <pointer>`. The pointer doesn't exist for this connection. Call `get_navigation` without a pointer to see the outline, or use `find` to locate the entry by title.
</Expandable>
